# Quickstart: 動作検証ガイド

本機能(P1〜P5、spec.md参照)がエンドツーエンドで機能することを確認するための手順。実装の詳細やコードは含めない。API契約は[contracts/api.md](./contracts/api.md)、データ構造は[data-model.md](./data-model.md)を参照。

**重要**: 重い計算(調整アルゴリズムの実行、Google Sheets/start.ggの読み書き)はすべてブラウザ内で完結する(research.md #1)。制御プレーン(Cloudflare Workers)は実行ロック・パラメータ設定・公開結果キャッシュのみを扱う。

## 前提条件

- Googleアカウント(検証用スプレッドシートを1つ作成できること)
- （US4を検証する場合)start.gg個人アクセストークンを発行できるstart.ggアカウントと、テスト用イベント/フェーズへの運営権限
- 制御プレーン(Cloudflare Workers + D1)、GitHub Actionsの`indexer`ワークフロー、indexerの成果物(MatchHistoryIndex、Parquet形式)がデプロイ・公開済みであること。いずれのサービスにも支払い手段は登録しないこと(research.md #0)
- フロントエンド(GitHub Pages)が制御プレーンAPIのオリジンを指す設定でビルド・デプロイ済みであり、初回実行時にPyodide/DuckDB-WASMを読み込めること

## シナリオ1: Googleスプレッドシートでのシード自動調整(US1, P1)

1. 検証用スプレッドシートに、既存ノートブックと同じ列構成(選手識別ID・表示名・非公開評価値・任意のWave希望等)でシード表を1シート用意する。
2. フロントエンドの設定ページにアクセスし、Googleアカウントを連携する(Google Identity Servicesのサインインボタン操作のみで完結し、バックエンドへのリダイレクトは発生しない。research.md #5)。
3. 実行ページで入力元として「Googleスプレッドシート」を選び、対象スプレッドシートIDとワークシート名を指定して実行する。フロントエンドは`POST /runs`でロックを取得した後、ブラウザ内(Pyodide + DuckDB-WASM)で計算を開始する。
4. 実行中、フロントエンドが定期的に`POST /runs/{runId}/heartbeat`を送っていること、`GET /runs/{runId}`の`status`が`queued` → `running`と遷移することを確認する。
5. 計算完了後、ブラウザが直接元のスプレッドシートに新しいシートを追記すること、あわせて`POST /runs/{runId}/complete`が呼ばれ`status`が`succeeded`になることを確認する(FR-009, FR-007)。
6. **期待結果**: 既存のシートやデータが上書きされていないこと、上位固定シード数(設定した場合)が元の順序のまま維持されていること(FR-005)。

## シナリオ2: 実行中の状況把握と多重実行防止(US2, P2)

1. シナリオ1の手順3で実行を開始した状態で、実行状況ページに現在の状況(`running`)が表示されることを確認する。
2. 実行中にタブを閉じよう(または別ページへ遷移しよう)とすると、処理が中断される可能性がある旨の警告が表示されることを確認する(FR-013)。
3. 実際にタブを閉じて処理を中断させ、一定時間(ハートビートのタイムアウト。research.md #4)経過後に`GET /runs/{runId}`の`status`が`failed`になることを確認する。
4. 同一の対象に対して改めてシード自動調整を実行し、正常に完了できることを確認する(FR-013)。
5. 同一の対象に対して実行中(ハートビート有効期限内)に別タブから再度実行を開始しようとし、`POST /runs` が409(`RUN_IN_PROGRESS`)を返すことを確認する(FR-013a)。

## シナリオ3: 結果表示ページでの振り返り(US3, P3)

1. シナリオ1で得た`runId`を用いて、認証していないブラウザ(シークレットウィンドウ等)から `GET /public/results/{runId}` を裏で呼び出す結果表示ページにアクセスする。
2. **期待結果**: 認証を要求されずに調整前後のシード比較・配置理由が表示され、`hiddenValue`に相当する値がレスポンス・画面のどこにも含まれないこと(FR-012b)。このページはPyodide/DuckDB-WASMを読み込まないこと(閲覧のみなら計算不要のため)。
3. 同一対象に対して2回目の実行を行った後、結果表示ページの「過去の実行一覧」(`GET /public/runs?targetId=...`)から1回目の実行結果を選び直せることを確認する(FR-016)。
4. Wave希望を満たせない選手が出るような入力(希望Waveが埋まらない組み合わせ)で実行し、結果表示ページに違反者一覧が強調表示されることを確認する(FR-006)。

## シナリオ4: start.ggからの読み込み・書き戻し(US4, P4)

1. 設定ページでstart.gg個人アクセストークンを入力する。ブラウザのIndexedDBに保存され、いかなるサーバーにも送信されないことをネットワークタブで確認する(research.md #6)。
2. 監査ログ用スプレッドシートが未接続の状態で実行を試み、`POST /runs` が428(`AUDIT_SPREADSHEET_REQUIRED`)を返すことを確認する(FR-012a)。
3. 監査ログ用スプレッドシートを接続(または自動作成)した上で、入力元を「start.gg」に切り替え、対象イベント/フェーズを指定して実行する。ブラウザが直接start.gg APIを呼び出す(またはCORS未対応の場合は`POST /relay/startgg`経由。research.md #7)ことをネットワークタブで確認する。
4. 実行完了後、`writebackApproved`が`false`であること、start.gg側のシードがまだ変更されていないことを確認する(FR-011)。
5. 確認画面で書き戻しを承認する。ブラウザが直接start.gg APIへ書き戻しを実行した後、`POST /runs/{runId}/writeback-recorded`が呼ばれ、start.gg側のシード設定が調整後の順序に更新されていることを確認する。
6. 監査ログ用スプレッドシートに、調整前(Startgg上で仮組みされていた時点)のシード順が個人情報を含まない別シートとして保存されていることを確認する(FR-012c)。

## シナリオ5: 設定ページでの簡易パラメータ設定(US5, P5)

1. 初めて設定ページにアクセスし、パラメータ調整用のYes/No質問にすべて回答する(`PUT /settings/{targetId}`の`wizardAnswers`)。
2. `GET /settings/{targetId}` で`resolvedDefaults`が回答の組み合わせに応じて設定されていることを確認する(FR-018)。
3. 特定のパラメータ(例: 固定シード数)のみ個別値で上書きし、後続の実行(`settingsSnapshot`)にその上書き値が反映されていることを確認する(FR-019)。

## 非機能要件の確認

- **60分以内の完了(SC-002)**: 数百人規模相当のテストデータで、一般的なノートPCのブラウザで実行し、完了までの時間が60分以内であることを確認する。
- **大規模大会での警告表示・実行継続(FR-003a, SC-002a)**: 意図的に極端な参加者数のテストデータで実行し、`POST /runs` が拒否(4xx)ではなく202を返し、`sizeWarning`に想定処理時間・参加者数が含まれること、「タブを開いたままにしてください」旨の案内が表示されることを確認する。さらに、その実行が拒否されずに`running`へ進み、60分を超えても(タブを開いたままであれば)完了まで継続することを確認する。
- **データ取得サイズ・時間(FR-002、research.md #2実測調査)**: ブラウザの開発者ツール(Networkタブ)で、smash_database全体ではなくMatchHistoryIndex(圧縮Parquetアーティファクト)のみをダウンロードしていること、そのサイズが実測見積もり(全期間・全地域で概ね1桁MB台〜十数MB程度)から大きく外れていないこと、ダウンロードが数秒程度で完了することを確認する。indexerの実装後、この数値が見積もりと大きく乖離する場合は参照期間の上限を短縮する。
- **メモリ制約(FR-002)**: 実行時のブラウザタブのメモリ使用量(開発者ツールのPerformance/Memoryタブ)が一般的な上限を超えていないことを確認する。
- **キャッシュの有効性(research.md #2)**: 同一ブラウザで同じ対象に対して2回目の実行を行った際、Pyodide/DuckDB-WASMおよびインデックス(indexerが更新していない場合)が再ダウンロードされず、キャッシュから読み込まれることをNetworkタブで確認する。
- **課金が発生しないこと(SC-005)**: Cloudflare/GitHubいずれのアカウントにも支払い手段が登録されていないことを確認した上で、`/runs`を短時間に連続で呼び出し、無料枠を超えた場合に課金ではなく明示的なエラー応答(レート制限等)になることを確認する(research.md #0)。
- **認証情報がサーバーに送信・保存されないこと(research.md #5, #6)**: 実行前後を通じて、Cloudflare Workers宛のいかなるリクエストにもGoogleアクセストークン・start.ggトークンの値が含まれないことをネットワークタブで確認する。Cloudflare Workers・GitHub Actionsいずれのログにもこれらの値が出力されないことを確認する。
- **多重実行ロックの自動失効(research.md #4)**: 実行中のタブを強制終了し、ハートビートのタイムアウト時間経過後に対象への新規実行がブロックされなくなること(`POST /runs`が409を返さなくなること)を確認する。
