# Quickstart: 動作検証ガイド

本機能(P1〜P5、spec.md参照)がエンドツーエンドで機能することを確認するための手順。実装の詳細やコードは含めない。API契約は[contracts/api.md](./contracts/api.md)、データ構造は[data-model.md](./data-model.md)を参照。

## 前提条件

- Googleアカウント(検証用スプレッドシートを1つ作成できること)
- （US4を検証する場合）start.gg個人アクセストークンを発行できるstart.ggアカウントと、テスト用イベント/フェーズへの運営権限
- 制御プレーン(Cloudflare Workers + D1)、GitHub Actionsワークフロー(`run-adjustment` / `indexer`)、indexerの成果物(MatchHistoryIndex)がデプロイ・公開済みであること。いずれのサービスにも支払い手段は登録しないこと(research.md #0)
- フロントエンド(GitHub Pages)が制御プレーンAPIのオリジンを指す設定でビルド・デプロイ済みであること

## シナリオ1: Googleスプレッドシートでのシード自動調整(US1, P1)

1. 検証用スプレッドシートに、既存ノートブックと同じ列構成(選手識別ID・表示名・非公開評価値・任意のWave希望等)でシード表を1シート用意する。
2. フロントエンドの設定ページにアクセスし、Googleアカウントを連携する(`POST /auth/google/start` → OAuth同意画面 → `GET /auth/google/callback`)。
3. 実行ページで入力元として「Googleスプレッドシート」を選び、対象スプレッドシートIDとワークシート名を指定して実行する(`POST /runs`)。
4. `GET /runs/{runId}` をポーリングし、`status` が `queued` → `running` → `succeeded` と遷移することを確認する。
5. 元のスプレッドシートに新しいシートが追記され、調整後のシード順・判断根拠ログが含まれることを確認する(FR-009, FR-007)。
6. **期待結果**: 既存のシートやデータが上書きされていないこと、上位固定シード数(設定した場合)が元の順序のまま維持されていること(FR-005)。

## シナリオ2: タブを閉じても続くバックグラウンド実行(US2, P2)

1. シナリオ1の手順3で実行を開始した直後にブラウザタブを閉じる。
2. 数分後、フロントエンドを再度開き、同じ`runId`の結果ページ(または実行状況ページ)にアクセスする。
3. **期待結果**: `GET /runs/{runId}` が `succeeded`(または処理継続中なら`running`)を返し、処理が中断されていないこと(FR-013)。
4. 同一の対象に対して実行中に別タブから再度実行を開始しようとし、`POST /runs` が409(`RUN_IN_PROGRESS`)を返すことを確認する(FR-013a)。

## シナリオ3: 結果表示ページでの振り返り(US3, P3)

1. シナリオ1で得た`runId`を用いて、認証していないブラウザ(シークレットウィンドウ等)から `GET /public/results/{runId}` 相当の結果表示ページにアクセスする。
2. **期待結果**: 認証を要求されずに調整前後のシード比較・配置理由が表示され、`hiddenValue`に相当する値がレスポンス・画面のどこにも含まれないこと(FR-012b)。
3. 同一対象に対して2回目の実行を行った後、結果表示ページの「過去の実行一覧」(`GET /public/runs?targetId=...`)から1回目の実行結果を選び直せることを確認する(FR-016)。
4. Wave希望を満たせない選手が出るような入力(希望Waveが埋まらない組み合わせ)で実行し、結果表示ページに違反者一覧が強調表示されることを確認する(FR-006)。

## シナリオ4: start.ggからの読み込み・書き戻し(US4, P4)

1. 設定ページでstart.gg個人アクセストークンを登録する(`POST /auth/startgg/token`)。
2. 監査ログ用スプレッドシートが未接続の状態で実行を試み、`POST /runs` が428(`AUDIT_SPREADSHEET_REQUIRED`)を返すことを確認する(FR-012a)。
3. 監査ログ用スプレッドシートを接続(または自動作成)した上で、入力元を「start.gg」に切り替え、対象イベント/フェーズを指定して実行する。
4. 実行完了後、`writebackApproved`が`false`であること、start.gg側のシードがまだ変更されていないことを確認する(FR-011)。
5. `POST /runs/{runId}/writeback/approve` を呼び出し、start.gg側のシード設定が調整後の順序に更新されることを確認する。
6. 監査ログ用スプレッドシートに、調整前(Startgg上で仮組みされていた時点)のシード順が個人情報を含まない別シートとして保存されていることを確認する(FR-012c)。

## シナリオ5: 設定ページでの簡易パラメータ設定(US5, P5)

1. 初めて設定ページにアクセスし、パラメータ調整用のYes/No質問にすべて回答する(`PUT /settings/{targetId}`の`wizardAnswers`)。
2. `GET /settings/{targetId}` で`resolvedDefaults`が回答の組み合わせに応じて設定されていることを確認する(FR-018)。
3. 特定のパラメータ(例: 固定シード数)のみ個別値で上書きし、後続の実行(`settingsSnapshot`)にその上書き値が反映されていることを確認する(FR-019)。

## 非機能要件の確認

- **60分以内の完了(SC-002)**: 数百人規模相当のテストデータで実行し、`finishedAt - startedAt` が60分以内であることを確認する。
- **事前拒否(FR-003a)**: 意図的に極端な参加者数のテストデータで実行し、`POST /runs` が422(`ESTIMATED_TIME_EXCEEDED`)を返すことを確認する。
- **メモリ制約(FR-002)**: `run-adjustment`ワークフローの実行ログから、smash_database全体ではなくMatchHistoryIndex(圧縮アーティファクト)のみを取得していること、実行時のメモリ使用量がGitHub Actionsランナーの上限を超えていないことを確認する。
- **課金が発生しないこと(SC-005)**: Cloudflare/GitHubいずれのアカウントにも支払い手段が登録されていないことを確認した上で、`/runs`を短時間に連続で呼び出し、無料枠を超えた場合に課金ではなく明示的なエラー応答(レート制限・キュー待ち等)になることを確認する(research.md #0)。
- **トークン漏洩がないこと(research.md #3)**: `run-adjustment`ワークフローの実行ログ(公開リポジトリのため誰でも閲覧可能)に、Google/start.ggのアクセストークン・リフレッシュトークンが一切出力されていないことを確認する。
