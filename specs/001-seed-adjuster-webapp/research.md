# Phase 0 Research: 対戦相手シード調整ツールの公開Web化

各項目は spec.md の要件・制約から導かれた技術的な未決事項について、Decision / Rationale / Alternatives considered の形式でまとめる。

## 1. バックグラウンド実行基盤(FR-013, FR-003, SC-005)

**Decision**: Google Cloud Run Jobs を1回の調整実行(データ取得〜結果出力)の実行単位として用いる。フロントエンドからの実行トリガーは軽量な Cloud Run サービス(HTTP API)が受け付け、Jobs の実行を起動して即座に `runId` を返す。

**Rationale**: Cloud Run Jobs はリクエスト/レスポンスの往復を必要としないバッチ実行に向いており、ブラウザタブが閉じてもジョブの実行自体には影響しない(FR-013)。実行時間の上限も数時間単位まで設定でき、60分という要件(FR-003)を十分にカバーできる。Cloud Run は常時無料枠(リクエスト数・vCPU秒・メモリGB秒)があり、月あたり数大会程度の利用(SC-005)であれば無料枠内に収まる可能性が高い。

**Alternatives considered**:
- GitHub Actions の `workflow_dispatch` をジョブ実行に転用: 公開リポジトリなら無料だが、外部の任意利用者からのトリガーをGitHub Actions APIに安全に中継する構成が複雑になり、認証情報(GitHubトークン)の管理主体が不明瞭になるため見送り。
- ブラウザ内(WebAssembly等)での実行: タブを閉じると実行が止まるため、FR-013(タブを閉じても継続)を満たせず不採用。
- Cloud Functions (2nd gen) の長時間実行: Cloud Run Jobs と同等のことができるが、バッチ実行の意味論(リトライ・並列度制御なし)がCloud Run Jobsの方が素直であるため、より単純な選択肢を採用。

## 2. 実行状態・多重実行ロックの保管先(FR-013a, FR-014)

**Decision**: Firestore(Native mode)に `AdjustmentRun` ドキュメントと、入力対象ごとの実行ロック(`targetId` をキーとするトランザクショナルなロックドキュメント)を保持する。

**Rationale**: Firestore は無料枠が大きく、Cloud Run から低レイテンシで読み書きできる。トランザクションにより「実行中なら新規実行を拒否する」(FR-013a)というロック処理をレースコンディションなく実装できる。

**Alternatives considered**: Google スプレッドシート自体をロック管理に使う案は、書き込み競合の検出(トランザクション)が弱く、ポーリング前提になるため多重実行防止の信頼性が下がり不採用。

## 3. smash_database をメモリに収める方法(FR-002)

**Decision**: `indexer` コンポーネントが smash_database リポジトリを定期的に増分取得し、選手ペア単位の対戦タイムスタンプ・大会規模一覧に圧縮した小容量インデックス(1ファイル)を生成して静的に公開する(GitHub Releases アセットとして配布)。バックエンドは実行のたびに smash_database 全体をクローンせず、この圧縮インデックスのみを取得してメモリに載せる。近さ指標の計算式(経過時間に対して指数的に減衰)により、一定期間(既定: 数年)より古い対戦履歴は結果へほぼ寄与しないため、インデックスの参照範囲にはこの期間で上限を設ける。

**Rationale**: 現行ノートブックは smash_database 全体をクローンし全大会分のJSONを読み込んでいるが、これは対戦履歴が増え続ける限りいずれメモリ制約に抵触する。対戦履歴全体ではなく「選手ペア→対戦タイムスタンプ一覧」という調整計算に必要な最小限の情報だけを保持すれば、データ量は選手ペアの延べ対戦数に比例する程度に収まり、桁違いに小さくなる。indexer側では増分更新(前回処理済みの大会以降のみ走査)によって、smash_database自体が大きくても定期実行のたびに全件再走査する必要がなくなる。

**Alternatives considered**:
- 実行のたびに smash_database をシャローウォンで取得しその場で集計: シャロークローンでも履歴データそのものは大会数に比例して増え続けるため、根本的なメモリ制約解消にならず不採用。
- 対戦履歴をFirestore等のDBに全件投入しクエリで都度引く: 選手ペア×対戦のレコード数が多く無料枠を圧迫しやすいこと、smash_dataベース更新との同期の複雑さから、静的インデックスファイル配布より運用コストが高く不採用。

## 4. Google 認証方式(FR-001, FR-013, FR-017, FR-020)

**Decision**: 設定ページから開始する OAuth 2.0 認可コードフロー(Authorization Code Flow, offline access)を用いる。認可コードの交換はバックエンド(Cloud Run API)が行い、取得したリフレッシュトークンを暗号化してFirestoreに保存する。以降のシート読み書き(実行時・バックグラウンドジョブ実行時含む)はこのリフレッシュトークンから都度アクセストークンを取得して行う。

**Rationale**: バックグラウンドジョブ(タブを閉じても継続、FR-013)がGoogleスプレッドシートを読み書きするには、ブラウザセッションに依存しない長期的な認可(リフレッシュトークン)が必要であり、これは認可コードフローでのみ取得できる(クライアントサイドのみの Implicit Flow ではアクセストークンしか得られず、有効期限内にジョブが完了する保証がない)。認証情報の入力はすべて設定ページのOAuth同意画面によるボタン操作で完結し、利用者が環境変数やAPIキーを直接入力する必要はない(FR-017)。各利用者のトークンは他利用者と分離して保管され、書き込み系操作はそのアカウント自身の権限範囲に限定される(FR-020)。

**Alternatives considered**: サービスアカウントによる共有アクセスは、各利用者が自分のスプレッドシートを個別に共有設定する手間が生じる上、FR-020(利用者自身の権限範囲でのみアクセス)の原則にも反するため不採用(仕様策定時のAssumptionsで既に明示的に排除済み)。

## 5. start.gg 連携の認証方式(FR-010, FR-011)

**Decision**: 設定ページで、利用者自身が発行した start.gg 個人アクセストークン(Bearer token)を入力する方式を採用し、暗号化してFirestoreに保存する。将来的に start.gg が第三者向けOAuthアプリ登録を一般提供した場合は、Google連携と同様の認可コードフローへ移行可能な設計とする。

**Rationale**: start.gg の GraphQL API は個人アクセストークンによる認証が標準的な利用方法であり、追加の開発者審査を要するOAuthアプリ登録に依存せずに実装できる。トークンの入力は設定ページのフォームを通じて行われるため、FR-017(環境変数の直接編集をさせない)の要件は満たされる。書き戻し実行時にはトークンに紐づくアカウントの大会運営権限を start.gg 側のAPI呼び出し結果から確認し、権限不足時はFR-021に従い書き込みを行わない。

**Alternatives considered**: OAuthアプリとしての正式提供は、アプリ登録・審査のリードタイムが不確実であり、それ待ちで機能提供を遅らせるのは本機能の目的(誰でもすぐ使える)に反するため、初期実装では見送る。

## 6. 認証なしで結果を公開する方法(FR-012b, SC-008)

**Decision**: 結果表示ページ(フロントエンド)は、Cloud Run API が提供する公開エンドポイント `GET /public/results/{runId}` を認証なしで呼び出す。このエンドポイントはサーバー側で(実行者の資格情報を用いて)監査ログ用スプレッドシートから該当実行のデータを読み出し、非公開評価値(hidden_value)を除外して整形したJSONを返す。

**Rationale**: 結果を閲覧する第三者(選手・観戦者・共同運営メンバー)はGoogleアカウントを持たない、または当該スプレッドシートへのアクセス権を持たない前提のため、閲覧のたびにスプレッドシートへの直接アクセス権を要求するわけにはいかない。サーバー側で一度整形・サニタイズしたビューを返すことで、hidden_valueのような非公開項目を構造的に除外でき(FR-012b)、スプレッドシートの列追加など将来の変更にも安全に追従できる。

**Alternatives considered**: スプレッドシート自体を「リンクを知っている全員が閲覧可」に設定し、フロントエンドがSheets APIキーで直接読み取る方式は、実装が単純だが、hidden_value列を誤って公開してしまうリスクや、シートの生の列構成がそのままAPI利用者に露出する点で望ましくなく不採用。

## 7. 事前見積もりによる実行拒否のしきい値(FR-003a)

**Decision**: indexer/backendの実測ベンチマーク(想定される参加者数と処理時間の関係)から導いた「参加者数の目安上限」をバックエンド設定値として持ち、実行トリガー時にその値を超える場合のみ事前拒否する。しきい値は実装・運用開始後の実測に基づき継続的に調整可能なパラメータとして扱う(FR-003で明示している通り、この上限を主たる時間制約の充足手段にはしない)。

**Rationale**: 実際にどの参加者数から60分を超えるかは実装時のアルゴリズム最適化の結果に依存するため、仕様段階で具体的な数値を固定せず、実装・計測を経て決定する運用上のパラメータとして扱うのが妥当である。

**Alternatives considered**: 仕様レベルで固定の参加者数上限(例: 1000人)を定めることも検討したが、最適化の余地を狭めてしまい、FR-003の「処理の最適化を主対応とする」という方針と矛盾するため見送った。

## 8. フロントエンド技術選定

**Decision**: TypeScript + React + Vite による静的SPAとし、`vite build` の出力を GitHub Pages にデプロイする。

**Rationale**: GitHub Pages は静的ファイルのホスティングのみをサポートするため、ビルド時に完全な静的アセット一式を出力できるフレームワークが必要。Reactはエコシステム・採用実績が豊富で、設定ページのYes/Noウィザードや結果表示ページの表形式UIの実装に十分な部品(フォーム、テーブル)が揃っている。

**Alternatives considered**: Svelte/Vueも静的出力可能で有力な代替だが、機能要件上の優劣はなく、今回はエコシステムの厚さを優先してReactを選定した。将来的な変更を妨げるものではない。

## 9. バックエンド言語・フレームワーク選定

**Decision**: Python 3.12 + FastAPI。

**Rationale**: 既存のシード自動調整ロジック(`seed_adjuster.ipynb`)がPythonで実装されており、アルゴリズム(近さ指標計算・Wave制約処理・タイトグループ検出など)をほぼそのまま移植できるため、独自ロジックの再実装に伴う不具合混入リスクを最小化できる。FastAPIは型付きの入出力スキーマ定義とOpenAPI契約生成を標準でサポートし、`contracts/`で定義するAPI契約との整合を保ちやすい。

**Alternatives considered**: Node.js/TypeScriptで統一する案は、フロントエンドと言語を揃えられる利点はあるが、既存アルゴリズムの逐語的移植が難しくなり不採用。

## 10. コスト最小化の全体方針(SC-005)

**Decision**: すべてのマネージドサービス(Cloud Run, Cloud Run Jobs, Firestore)を各サービスの常時無料枠内に収まる設計とし、GitHub Pages・GitHub Actions(公開リポジトリ)は無料のまま用いる。有料が発生しうるのは「無料枠を超える極端な利用量」の場合のみとし、その場合の扱いは本機能の範囲外とする(spec.md Assumptions参照)。

**Rationale**: 依頼者の「料金をできる限り支払いたくない」という要望に応えつつ、完全無サーバーでは実現できない要件(バックグラウンド実行、公開結果API、多重実行ロック)を満たすために、最小限のサーバーレス構成を選択した。
