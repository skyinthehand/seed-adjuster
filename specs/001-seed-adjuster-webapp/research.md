# Phase 0 Research: 対戦相手シード調整ツールの公開Web化

各項目は spec.md の要件・制約から導かれた技術的な未決事項について、Decision / Rationale / Alternatives considered の形式でまとめる。

## 0. コスト設計の大原則(SC-005 再検討)

最初の設計案(Google Cloud Run / Cloud Run Jobs / Firestore Blaze)は、SC-005「典型的な利用量では追加の有料インフラ費用が発生しない」を**満たしていなかった**。理由は、Cloud Runのようなpay-as-you-go型サービスは無料枠を超えても処理を止めずに課金され続ける「fail-open」な性質を持ち、かつ本機能は認証済み利用者なら誰でも計算実行をトリガーできる公開ツールであるため、通常想定を超える連続実行(悪意・誤操作を問わず)が起きた場合に運用担当者へ実費請求が発生するリスクを構造的に排除できていなかったためである。

**Decision**: 「無料枠を超えたら処理が失敗する(fail-closed)」性質を持ち、かつ**支払い手段の登録なしに使える**サービスのみでアーキテクチャを構成する。具体的には、重い計算処理はGitHub Actions(公開リポジトリは無制限に無料)で実行し、トリガー・状態管理・公開APIはCloudflare Workers/D1(無料プランはカード登録不要、上限超過時はエラー応答であり課金ではない)で実装する。Google Cloudは、Google OAuthクライアントを登録するためだけに使い、**課金を有効化しない**(課金無効なプロジェクトは物理的に有料APIを呼び出せないため、伸ばそうにも実費が発生しえない)。

**Rationale**: これにより「典型的な利用量では無料」ではなく「無料枠を超えたら単に機能が一時停止するだけで、誰にも一切課金されない」という、より強い(検証可能な)性質としてSC-005を満たす。運用担当者はクレジットカードや請求先アカウントを一切登録する必要がなく、想定外の利用があっても最悪ケースは「動かなくなる」で止まる。

**Alternatives considered**:
- Cloud Billingの予算アラート + 自動停止Cloud Functionで防御する: 予算アラートの通知には遅延があり、また「自動停止」処理自体もCloud Functions等の追加コンポーネントを要し、その間の実費発生を完全には防げない。事後対応であって構造的な保証にならないため不採用。
- 利用量に上限を設けた上でCloud Runを使い続ける: 上限設定(Cloud Runの max instances 等)はコストの上振れ幅を抑えられるが、それでも支払いアカウントの登録自体は必須であり「誰にも課金されない」という強い保証にはならないため不採用。

## 1. 重い計算(調整実行本体、最大60分)の実行基盤(FR-013, FR-003, SC-005)

**Decision**: 本リポジトリ(公開リポジトリ)の GitHub Actions ワークフロー(`repository_dispatch` イベントで起動)として、1回の調整実行(データ取得〜結果出力)を実行する。

**Rationale**: 公開リポジトリのGitHub Actionsは実行時間・実行回数について課金が発生しない(無制限)。60分程度のジョブも標準のジョブタイムアウト設定内に収まる(FR-003)。ブラウザタブを閉じてもワークフロー実行自体は継続する(FR-013)。追加の支払いアカウント登録が一切不要であり、0番の大原則を満たす。

**Alternatives considered**:
- Google Cloud Run Jobs: 実行時間の柔軟性は高いが、課金アカウントの登録が必須でfail-open型のため0番の原則に反し不採用(当初案からの変更点)。
- ブラウザ内(WebAssembly等)での実行: タブを閉じると実行が止まるため、FR-013(タブを閉じても継続)を満たせず不採用。

## 2. トリガー・状態管理・公開APIの実行基盤(FR-013a, FR-014, FR-012b)

**Decision**: Cloudflare Workers(Freeプラン)上に、実行トリガー・実行状態問い合わせ・設定・公開結果取得のHTTP APIを実装する。状態(`AdjustmentRun`、対象ごとの多重実行ロック、`ConnectedAccount`、`AdjustmentSettings`)は Cloudflare D1(SQLiteベース、トランザクション対応)に保持する。

**Rationale**: Cloudflare WorkersのFreeプランはクレジットカード登録なしで利用開始でき、1日あたりのリクエスト数上限を超えても課金ではなくエラー応答になる(fail-closed)。D1はSQLiteのトランザクションを使えるため、「同一`targetId`への同時実行を1件に制限する」(FR-013a)というロックをレースコンディションなく実装できる。GitHub Actions側のジョブからも、Worker宛のHTTPS呼び出しで状態更新・完了報告ができる。

**Alternatives considered**: Firestore(Google Cloud)は無料のSparkプランであれば課金アカウント不要で使えるが、Cloud Runを廃止した後にわざわざ別クラウド(Google Cloud)の別プロダクトを併用する必要性が薄れたため、トリガー層と同じCloudflareでD1に統一し運用対象を減らした。

## 3. GitHub Actions ジョブへの認証情報の受け渡し(セキュリティ、FR-017, FR-020)

**Decision**: `repository_dispatch` の `client_payload` には内部の `runId` のみを渡す(Google/start.ggのトークンそのものは含めない)。ジョブは実行開始後、GitHub Actions の OIDC ID トークン(`permissions: id-token: write` で取得)を添えてCloudflare Worker の内部エンドポイント(`POST /internal/runs/{runId}/credentials`)を呼び出す。Workerは、このOIDCトークンの署名・発行者(`https://token.actions.githubusercontent.com`)・`repository`クレイム(本リポジトリと完全一致)を検証した上で、該当`runId`に対応する暗号化済みトークンを一度きりだけ復号して返す(同一`runId`への2回目の要求は拒否する)。

**Rationale**: 本リポジトリは無料のActions実行のためpublicである必要があり、public リポジトリのActions実行ログは誰でも閲覧できる。そのため、`workflow_dispatch`の入力値やジョブのログ出力に利用者のGoogle/start.ggトークンを一切含めてはならない。OIDCトークンによって「本当に自分自身のリポジトリの正規のワークフロー実行から呼ばれているか」をWorker側で暗号学的に検証できるため、トークンの受け渡しを安全に行える。一度きりの払い出し(single-use)にすることで、万一OIDC検証をすり抜けようとする試みがあっても被害を1回分の実行に限定できる。

**Alternatives considered**: GitHub Actions の暗号化シークレット(`secrets.*`)に利用者ごとのトークンを都度登録する方式は、Repository/Organization Secretsは管理者が事前登録する前提の仕組みであり、公開ツールの不特定多数の利用者ごとに動的追加する運用に向かないため不採用。

## 4. smash_database をメモリに収める方法(FR-002)

**Decision**: `indexer`(GitHub Actionsの定期実行ワークフロー)が smash_database リポジトリを定期的に増分取得し、選手ペア単位の対戦タイムスタンプ・大会規模一覧に圧縮した小容量インデックス(1ファイル)を生成し、GitHub Releases アセットとして公開する。調整実行ジョブは実行のたびに smash_database 全体をクローンせず、この圧縮インデックスのみを取得してメモリに載せる。近さ指標の計算式(経過時間に対して指数的に減衰)により、一定期間(既定: 数年)より古い対戦履歴は結果へほぼ寄与しないため、インデックスの参照範囲にはこの期間で上限を設ける。

**Rationale**: 現行ノートブックは smash_database 全体をクローンし全大会分のJSONを読み込んでいるが、これは対戦履歴が増え続ける限りいずれメモリ制約に抵触する。対戦履歴全体ではなく「選手ペア→対戦タイムスタンプ一覧」という調整計算に必要な最小限の情報だけを保持すれば、データ量は選手ペアの延べ対戦数に比例する程度に収まり、桁違いに小さくなる。indexer側では増分更新(前回処理済みの大会以降のみ走査)によって、smash_database自体が大きくても定期実行のたびに全件再走査する必要がなくなる。indexerの実行自体もGitHub Actionsのため無料で、0番の大原則とも整合する。

**Alternatives considered**:
- 実行のたびに smash_database をシャロークローンして都度集計: 履歴データそのものが大会数に比例して増え続けるため、根本的なメモリ制約解消にならず不採用。
- 対戦履歴をD1等のDBに全件投入しクエリで都度引く: 選手ペア×対戦のレコード数が多く無料枠を圧迫しやすく、smash_database更新との同期も複雑になるため、静的インデックスファイル配布より運用コストが高く不採用。

## 5. Google 認証方式(FR-001, FR-013, FR-017, FR-020)

**Decision**: 設定ページから開始する OAuth 2.0 認可コードフロー(Authorization Code Flow, offline access)を用いる。認可コードの交換は Cloudflare Worker が行い、取得したリフレッシュトークンを暗号化してD1に保存する。GitHub Actionsの調整実行ジョブは、3番の仕組みでこのリフレッシュトークンを取得し、都度アクセストークンに交換してシートを読み書きする。OAuthクライアントIDの登録には課金無効なGoogle Cloudプロジェクトを1つ用いる(0番参照)。

**Rationale**: バックグラウンド実行(タブを閉じても継続、FR-013)がGoogleスプレッドシートを読み書きするには、ブラウザセッションに依存しない長期的な認可(リフレッシュトークン)が必要であり、これは認可コードフローでのみ取得できる。認証情報の入力はすべて設定ページのOAuth同意画面によるボタン操作で完結し、利用者が環境変数やAPIキーを直接入力する必要はない(FR-017)。各利用者のトークンは他利用者と分離して保管され、書き込み系操作はそのアカウント自身の権限範囲に限定される(FR-020)。Google Sheets APIの呼び出し自体はGoogle側課金の対象ではなく(OAuthユーザークォータの範囲)、課金無効プロジェクトでも問題なく利用できる。

**Alternatives considered**: サービスアカウントによる共有アクセスは、各利用者が自分のスプレッドシートを個別に共有設定する手間が生じる上、FR-020(利用者自身の権限範囲でのみアクセス)の原則にも反するため不採用(仕様策定時のAssumptionsで既に明示的に排除済み)。

## 6. start.gg 連携の認証方式(FR-010, FR-011)

**Decision**: 設定ページで、利用者自身が発行した start.gg 個人アクセストークン(Bearer token)を入力する方式を採用し、暗号化してD1に保存する。将来的に start.gg が第三者向けOAuthアプリ登録を一般提供した場合は、Google連携と同様の認可コードフローへ移行可能な設計とする。

**Rationale**: start.gg の GraphQL API は個人アクセストークンによる認証が標準的な利用方法であり、追加の開発者審査を要するOAuthアプリ登録に依存せずに実装できる。トークンの入力は設定ページのフォームを通じて行われるため、FR-017(環境変数の直接編集をさせない)の要件は満たされる。書き戻し実行時にはトークンに紐づくアカウントの大会運営権限を start.gg 側のAPI呼び出し結果から確認し、権限不足時はFR-021に従い書き込みを行わない。

**Alternatives considered**: OAuthアプリとしての正式提供は、アプリ登録・審査のリードタイムが不確実であり、それ待ちで機能提供を遅らせるのは本機能の目的(誰でもすぐ使える)に反するため、初期実装では見送る。

## 7. 認証なしで結果を公開する方法(FR-012b, SC-008)

**Decision**: 結果表示ページ(フロントエンド)は、Cloudflare Worker が提供する公開エンドポイント `GET /public/results/{runId}` を認証なしで呼び出す。このエンドポイントはサーバー側で(実行者のトークンを用いて)監査ログ用スプレッドシートから該当実行のデータを読み出し、非公開評価値(hidden_value)を除外して整形したJSONを返す。

**Rationale**: 結果を閲覧する第三者(選手・観戦者・共同運営メンバー)はGoogleアカウントを持たない、または当該スプレッドシートへのアクセス権を持たない前提のため、閲覧のたびにスプレッドシートへの直接アクセス権を要求するわけにはいかない。サーバー側で一度整形・サニタイズしたビューを返すことで、hidden_valueのような非公開項目を構造的に除外でき(FR-012b)、スプレッドシートの列追加など将来の変更にも安全に追従できる。Cloudflare Workersの無料リクエスト数上限内であれば、この読み取りAPIも追加費用なしで提供できる。

**Alternatives considered**: スプレッドシート自体を「リンクを知っている全員が閲覧可」に設定し、フロントエンドがSheets APIキーで直接読み取る方式は、実装が単純だが、hidden_value列を誤って公開してしまうリスクや、シートの生の列構成がそのままAPI利用者に露出する点で望ましくなく不採用。

## 8. 事前見積もりによる実行拒否のしきい値(FR-003a)

**Decision**: 実測ベンチマーク(想定される参加者数と処理時間の関係)から導いた「参加者数の目安上限」を Worker 側の設定値として持ち、実行トリガー時にその値を超える場合のみ事前拒否する。しきい値は実装・運用開始後の実測に基づき継続的に調整可能なパラメータとして扱う(FR-003で明示している通り、この上限を主たる時間制約の充足手段にはしない)。

**Rationale**: 実際にどの参加者数から60分を超えるかは実装時のアルゴリズム最適化の結果に依存するため、仕様段階で具体的な数値を固定せず、実装・計測を経て決定する運用上のパラメータとして扱うのが妥当である。なお、GitHub Actionsには同時実行数の実用上の上限があるため、この事前拒否としきい値運用は、コスト面だけでなく「他の利用者の実行が渋滞しないための公平性」の観点でも意味を持つ。

**Alternatives considered**: 仕様レベルで固定の参加者数上限(例: 1000人)を定めることも検討したが、最適化の余地を狭めてしまい、FR-003の「処理の最適化を主対応とする」という方針と矛盾するため見送った。

## 9. フロントエンド技術選定

**Decision**: TypeScript + React + Vite による静的SPAとし、`vite build` の出力を GitHub Pages にデプロイする。

**Rationale**: GitHub Pages は静的ファイルのホスティングのみをサポートするため、ビルド時に完全な静的アセット一式を出力できるフレームワークが必要。Reactはエコシステム・採用実績が豊富で、設定ページのYes/Noウィザードや結果表示ページの表形式UIの実装に十分な部品(フォーム、テーブル)が揃っている。GitHub Pagesは静的ホスティングのみで課金対象の可変コンピュートを持たないため、0番の大原則とも自然に整合する。

**Alternatives considered**: Svelte/Vueも静的出力可能で有力な代替だが、機能要件上の優劣はなく、今回はエコシステムの厚さを優先してReactを選定した。将来的な変更を妨げるものではない。

## 10. トリガー/制御プレーンの言語・フレームワーク選定

**Decision**: Cloudflare Workers上の制御プレーン(OAuth・設定・実行トリガー・公開結果API)は TypeScript で実装する。実際の調整計算アルゴリズム(GitHub Actionsジョブとして実行)は Python 3.12 で実装し、`seed_adjuster.ipynb` のロジックを移植する。

**Rationale**: Cloudflare Workersのランタイムはネイティブに TypeScript/JavaScript をサポートしており、制御プレーンをそのまま実装できる。一方、既存のシード自動調整ロジック(近さ指標計算・Wave制約処理・タイトグループ検出など)はPythonで実装されているため、計算本体はPythonのまま移植することで、独自ロジックの再実装に伴う不具合混入リスクを最小化する。GitHub Actionsの標準ランナーはPythonの実行環境を標準サポートしており追加コストなく実行できる。

**Alternatives considered**: 制御プレーンと計算本体を同一言語(TypeScriptまたはPython)に統一する案も検討したが、Cloudflare WorkersでのPython実行はベータ機能であり本番運用の前提とするには時期尚早、また計算本体をTypeScriptへ逐語移植すると既存ロジックの検証負荷が高くなるため、実行基盤ごとに適した言語を採用する現行案とした。

## 11. コスト最小化の全体方針(SC-005) まとめ

**Decision**: アーキテクチャを構成する全コンポーネント(GitHub Pages、GitHub Actions[本体・indexer]、Cloudflare Workers/D1、Google Cloud[OAuthクライアント登録のみ・課金無効])のいずれについても、運用担当者は支払い手段(クレジットカード等)を一切登録しない。無料枠を超えた場合の挙動は「機能の一時的な利用不可(エラー・キュー待ち)」であり、実費請求は構造的に発生しない。

**Rationale**: 依頼者の「料金をできる限り支払いたくない」という要望に対し、「無料枠に収まる見込み」という運用上の期待ではなく、「そもそも支払い手段が登録されていないため課金されようがない」という設計上の性質でSC-005を保証する。将来的に無料枠では利用量を賄えなくなった場合は、それを機能改善の意思決定(有料プランへの移行を検討するタイミング)として扱えばよく、意図せず費用が発生することはない。
