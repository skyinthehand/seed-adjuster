# Feature Specification: 選手別の配置判断根拠の詳細確認

**Feature Branch**: `002-result-decision-detail`

**Created**: 2026-09-14

**Status**: Draft

**Input**: User description: "既存の対戦相手シード調整ツール(specs/001-seed-adjuster-webapp)の結果表示ページ(ResultsPage.tsx, /results/:runId)に、選手ごとの配置判断根拠を詳しく確認できるUIを追加する。背景: FR-007/FR-012/FR-012a/FR-012bにより「なぜその調整になったのか後から確認できる」画面(ResultsPage.tsx)は既に存在するが、配置理由(decisionLog)が選手ごとの行とは別に画面下へフラットな箇条書きで表示されており、各選手の行から直接確認できない。要件: 調整前後のシード比較表の各選手行に「詳細」ボタンを追加し、クリックするとモーダルが開く(画面が狭い場合を想定し、ホバー式のツールチップではなくボタン+モーダル形式を採用)。モーダルには次の情報を表示する: (1) その選手の元のシード順位、(2) 配置を決める際に比較した対戦相手候補を近い順に列挙し、各候補について算出された近さ指標の値・実際に対戦した大会名(複数ある場合は全件)・対戦日時、(3) 採用された判定ロジックの種別、(4) 最終的にどう調整されたか。対象ユーザーは既存と同じ(大会運営者、および結果を見る一般参加者向けの公開結果ページ)。既存のP1〜P5のユーザーストーリーとは独立した追加機能として新しいSpec Kitフィーチャーとして立てる。"

## Clarifications

### Session 2026-09-14

- Q: 比較対象の対戦相手候補との間に実際の対戦記録が1件もない場合、対戦実績欄には何を表示するか? → A: 「対戦履歴なし」等を明示し、他の情報(近さの指標値など)は通常通り表示する
- Q: 同じ対戦相手候補と、同じ大会・同じ日付で複数回対戦していた場合、対戦実績の一覧ではどう表示するか? → A: 同じ大会・同じ日付の対戦はまとめて1件とし、対戦回数を併記する
- Q: 大会名の解決に時間がかかっている間、詳細確認の画面はどう振る舞うか? → A: 詳細確認はすぐに開き、大会名欄だけ「読み込み中」等の一時表示から解決後に差し替わる

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 選手の行から配置判断根拠を直接確認する (Priority: P1)

結果ページ(`/results/:runId`)で調整前後のシード比較を見ている利用者(大会運営者、または結果を見る参加者)が、気になった選手の行から直接、その選手が現在の位置に配置された根拠(元の順位・比較された対戦相手候補・採用された判定ロジック・調整後の最終順位)を確認できる。

**Why this priority**: 001フィーチャーのFR-007/FR-012で「なぜその調整になったのか後から確認できるようにしたい」という当初の目的自体には既に対応済みだが、判断根拠が選手ごとの行とは別の場所にフラットな一覧として表示されており、特定の選手について知りたいときに該当箇所を目で探す必要がある。これを選手の行から直接開けるようにすることは、既存機能の価値を実際に使いやすくする土台であり、最優先で対応する。

**Independent Test**: 結果ページを開き、任意の選手の行から詳細を確認する操作を行い、その選手の元の順位・比較した対戦相手候補一覧・近さの指標値・採用ロジック・調整後の順位が、他の選手の情報と混在せず単独で確認できることを検証する。

**Acceptance Scenarios**:

1. **Given** 調整結果が表示された結果ページ、**When** 利用者がある選手の行から詳細確認の操作を行う、**Then** その選手の元の順位・比較した対戦相手候補(近い順)・各候補の近さの指標値・採用された判定ロジックの種別・調整後の最終順位が表示される。
2. **Given** 詳細確認の表示が開いている状態、**When** 利用者が別の選手の行から詳細確認を行う、**Then** 表示内容が新しく選んだ選手のものに切り替わり、前の選手の情報と混在しない。
3. **Given** 比較対象となる対戦相手候補が存在しない選手(例: 調整対象から外れて固定された上位シード)、**When** 利用者がその選手の詳細を確認する、**Then** 比較対象がなかった旨が分かりやすく示される(エラーにはならない)。

---

### User Story 2 - 対戦相手候補の実際の対戦大会・日時を確認する (Priority: P2)

詳細確認を見ている利用者が、比較された対戦相手候補それぞれについて、算出された近さの指標値の数字だけでなく、実際にどの大会・いつ対戦したのかを確認できる。

**Why this priority**: User Story 1で判断根拠そのものは確認できるようになるが、近さの指標値は抽象的な数値であり、「本当に対戦したのか、それはいつのどの大会か」を具体的に確認できることで、調整結果への納得感・検証可能性が大きく高まる。User Story 1の基盤があってこそ意味を持つ拡張のため、次点の優先度とする。

**Independent Test**: 詳細確認の中で、対戦相手候補の1件を選び、実際に対戦した大会名と対戦日時(複数回対戦している場合はその全件)が表示されることを、既知の対戦実績を持つ選手ペアで検証する。

**Acceptance Scenarios**:

1. **Given** 詳細確認が表示されている状態、**When** 利用者が対戦相手候補の一覧を見る、**Then** 各候補について、実際に対戦した大会名と対戦日時の一覧が表示される。
2. **Given** ある対戦相手候補と過去に複数回対戦している、**When** 利用者がその候補の対戦実績を確認する、**Then** すべての対戦(大会名・日時)が列挙される。
3. **Given** 大会名の情報が何らかの理由で解決できない、**When** 利用者が該当する対戦相手候補を確認する、**Then** 大会名が不明である旨が示されるが、他の情報(近さの指標値・対戦日時等)の表示は妨げられない。

---

### Edge Cases

- 比較対象の対戦相手候補が0件の選手(固定シードや、対戦履歴インデックスの参照期間より前の選手のみで構成される場合)はどう表示されるか?
- Wave希望により通常の判定ロジックが無視された選手について、その旨は判断根拠の詳細内でどう示されるか?
- 対戦大会名の情報源(対戦履歴インデックス側の対応表)の取得が遅延・失敗した場合、詳細確認はすぐ開き、大会名欄のみ「読み込み中」等の一時表示を経て解決後に差し替わる(Clarifications参照)。他の判断根拠情報の表示は待たされない。この差し替えによって、閉じるボタン等の操作可能な要素の位置はずれてはならない(FR-008)。
- 画面幅が狭い端末(スマートフォン等)で詳細確認を開いた場合、情報量が多くても操作・閲覧に支障がないか?
- 同じ選手が同じ大会・同じ日付で複数回(異なるラウンドなど)対戦していた場合は、まとめて1件・対戦回数併記で表示する(Clarifications参照)。異なる大会・異なる日付での対戦との混同がないよう区別する。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、結果ページの調整前後のシード比較表において、各選手の行から、その選手個別の配置判断根拠を確認できる操作を提供しなければならない。
- **FR-002**: 選手の配置判断根拠には、少なくとも次を含めなければならない: (a) その選手の元のシード順位、(b) 配置決定時に比較された対戦相手候補の一覧(近い順)、(c) 各対戦相手候補について算出された近さの指標値、(d) 採用された判定ロジックの種別、(e) 調整後の最終順位。
- **FR-003**: システムは、比較された対戦相手候補ごとに、実際に対戦した大会名と対戦日時を確認できる形で提示しなければならない。同じ大会・同じ日付での対戦が複数回ある場合は、まとめて1件とし対戦回数を併記しなければならない(異なる大会・異なる日付の対戦は、それぞれ別件として提示する)。その候補との実際の対戦記録が1件もない場合は、対戦履歴がない旨を明示しなければならない(その場合も、近さの指標値など他の情報は通常通り表示する)。
- **FR-004**: 対戦相手候補との実際の対戦について、大会名の情報が解決できない場合、システムはその旨を明示しつつ、近さの指標値や対戦日時など他の判断根拠情報の表示を妨げてはならない。
- **FR-005**: 配置判断根拠の詳細確認は、画面幅に関わらず(スマートフォン等の狭い画面を含む)利用できなければならない。
- **FR-006**: Wave希望(既存機能)により通常の判定ロジックが無視された選手については、その選手の配置判断根拠の中でその旨を明示しなければならない。
- **FR-007**: 選手の配置判断根拠を確認する操作は、結果ページの既存の公開性(認証不要でのアクセス、FR-012b)を変更してはならない。
- **FR-008**: 大会名が読み込み中の一時表示から解決後の表示へ差し替わる際、その差し替えによって画面内の操作可能な要素(閉じるボタン等)の位置がずれてはならない。

### Key Entities

- **配置判断根拠(PlacementDecisionDetail)**: ある選手が現在の位置に配置された理由を表す。元のシード順位、比較された対戦相手候補の一覧、採用された判定ロジックの種別、調整後の最終順位を保持する。既存の判断根拠ログ(DecisionLog)を選手単位で参照しやすくしたもの。
- **比較対象候補(ComparedCandidate)**: 配置判断根拠の中で比較された1人の対戦相手候補を表す。相手選手名、算出された近さの指標値、実際の対戦実績の一覧(大会名・対戦日時、0件の場合もあり、その場合は対戦履歴なしという意味を持つ)を保持する。
- **対戦実績(MatchRecord)**: 比較対象候補との、同じ大会・同じ日付における対戦のまとまりを表す。対戦した大会の名称、対戦日時、その大会・日付での対戦回数を保持する。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 結果ページを見ている利用者は、任意の選手の行から2回以内の操作で、その選手の配置判断根拠の詳細を確認できる。
- **SC-002**: 利用者は、比較された対戦相手候補ごとに実際の対戦大会名・日時を確認でき、近さの指標値が抽象的な数字だけでなく実際の対戦実績に基づくことを追跡できる。
- **SC-003**: 画面幅375px相当(一般的なスマートフォンの表示幅)でも、配置判断根拠の詳細確認のレイアウトが崩れず、すべての情報が閲覧できる。
- **SC-004**: 大会名の解決が遅延・失敗した場合でも、詳細確認はすぐに開き、利用者は他の判断根拠情報(元の順位・近さの指標値・対戦日時・採用ロジック・調整後順位)を待たされずに確認できる。大会名欄のみ一時的な表示を経て後から解決されるが、その差し替えの前後で画面内の操作可能な要素(閉じるボタン等)の位置は変わらない。

## Assumptions

- 大会名は対戦履歴データの提供元にある名称をそのまま表示し、翻訳や表記の統一・整形は行わない。
- 対戦日時は日付単位の精度で十分とする(時刻までの精度は要求しない)。
- 大会名の解決に使う情報源は、既存の対戦履歴インデックスの仕組み(001フィーチャーで構築済み)を拡張することで提供され、利用者が毎回大きなデータセットをすべて取得する必要はない。
- 本フィーチャーは既存の001フィーチャー(対戦相手シード調整ツール)のP1〜P5ユーザーストーリーの実装を前提とし、それらの挙動を変更しない。
- 対戦相手候補との近さの指標値の算出ロジック自体(近さの計算方法)は本フィーチャーの範囲外であり、既存のロジックをそのまま用いる。
