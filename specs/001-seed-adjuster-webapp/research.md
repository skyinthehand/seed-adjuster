# Phase 0 Research: 対戦相手シード調整ツールの公開Web化

各項目は spec.md の要件・制約から導かれた技術的な未決事項について、Decision / Rationale / Alternatives considered の形式でまとめる。

**改訂履歴**:
- 当初はGitHub Actions上でサーバー側計算(compute)を行う設計だったが、依頼者の指示により「重い計算はサーバーを介さずブラウザ内で完結させる(DuckDB-WASM等でローカルにデータを持ってきて計算する)」方針へ全面的に転換した(旧#1・旧#3を置き換え・廃止)。あわせて「実行中にタブを閉じても処理が継続する」(旧FR-013)は必須要件から希望要件に格下げされた。
- さらに、上記の転換を踏まえて依頼者と検討した結果、**同一対象への多重実行防止ロック(旧FR-013a)、およびそれを支えていたハートビート機構(旧#4)を撤回**した。当初の目的だった「共有計算資源の浪費防止」はクライアントサイド化により該当しなくなり、残るリスク(Startgg書き戻し時の後勝ち上書き、監査ログの紛らわしい重複)は許容範囲と判断されたため(spec.md Clarifications参照)。これに伴い本ドキュメントの節番号を振り直している。

## 0. コスト設計の大原則(SC-005 再検討)

**Decision**: 「無料枠を超えたら処理が失敗する(fail-closed)」性質を持ち、かつ**支払い手段の登録なしに使える**サービスのみでアーキテクチャを構成するという大原則を維持する。今回の方針転換(重い計算のクライアントサイド化)により、この原則はさらに強化される。トリガー・状態管理・公開結果キャッシュのみを担うCloudflare Workers/D1(無料プランはカード登録なし、上限超過時はエラー応答であり課金ではない)を薄く用い、Google Cloudは、Google OAuthクライアントを登録するためだけに使い、**課金を有効化しない**。

**Rationale**: 重い計算(調整アルゴリズム・対戦履歴クエリ)が運営者自身のブラウザ上で行われるようになったことで、そもそも「課金対象になりうるサーバー計算資源」自体がアーキテクチャから消える。残るサーバー的コンポーネント(Cloudflare Workers/D1、indexer用GitHub Actions)はいずれも無料プランの範囲でfail-closedに運用できるため、「無料枠を超えたら単に機能が一時停止するだけで、誰にも一切課金されない」という性質を、以前の設計(GitHub Actionsでサーバー側計算)よりもさらに単純な形で満たせる。

**Alternatives considered**: GitHub Actionsでサーバー側計算を行う設計(前回改訂までの案)は、それ自体はfail-closedでコスト面の原則を満たしていたが、OIDCによる資格情報受け渡しなど付随する複雑さがあった。依頼者からの明確な指示(クライアントサイド化)により、よりシンプルな現行案へ転換した。

## 1. 重い計算(調整アルゴリズム・対戦履歴クエリ)の実行場所

**Decision**: シード自動調整の計算は、サーバー側コンポーネントを持たず、**運営者のブラウザ内で完結**させる。具体的には、対戦履歴インデックス(2番参照)に対するクエリには DuckDB-WASM(ブラウザ内で動くWASM版DuckDB)を用い、調整アルゴリズム本体(近さ指標計算・Wave制約処理・タイトグループ検出など、`seed_adjuster.ipynb`由来のロジック)は Pyodide(ブラウザ内で動くWASM版Python)上でそのまま実行する。

**Rationale**: 依頼者から「DuckDB-WASMでローカルにデータを全部持ってきて、ローカルで計算させる」との明確な指示があった。この方式には次の利点がある。
- **コスト**: 重い計算がユーザーのデバイス上で行われるため、サーバー側の計算コスト・課金リスクが構造的に存在しない(0番の大原則をさらに強化)。
- **アルゴリズムの再利用**: Pyodideを使うことで、既存のPython実装(`seed_adjuster.ipynb`)をほぼそのまま再利用でき、TypeScriptへの逐語移植に伴う再実装リスク(不具合混入)を避けられる。これは以前の設計判断(「既存ロジックの再実装リスクを最小化する」)の考え方を、実行場所がブラウザに変わっても引き継ぐものである。
- **対戦履歴クエリの効率**: DuckDB-WASMは列指向の分析エンジンであり、選手ペア単位の対戦履歴という表形式データに対するクエリ(集計・フィルタ)を、素朴なJS/Pythonの辞書探索よりも効率的に行える。

**トレードオフ(意図的に許容)**: 実行中にブラウザタブを閉じると計算は中断される。これは以前必須要件だったFR-013の内容と衝突するが、依頼者の指示により「タブを閉じても継続する」ことは希望要件へ格下げされ、この制約を受け入れることが明示的に許容されている。また、初回実行時にDuckDB-WASMとPyodideの実行環境(WASMランタイム、あわせて数十MB程度)をダウンロードする必要があり、これは実行ボタンを押した際に遅延読み込み(lazy load)することで、結果閲覧のみを行う訪問者(公開結果ページの閲覧者)に不要な負荷をかけないようにする。

**異なる対象間の並列実行**: 計算が各利用者のブラウザで独立に行われるため、以前案にあった「GitHub Actionsの同時ジョブ数枠を巡る利用者間の競合」は構造的に発生しない。また、同一対象への多重実行そのものも禁止しない(3番参照。旧FR-013aは撤回済み)ため、異なる大会はもちろん同一大会への複数実行も互いにブロックし合わない。

**Alternatives considered**:
- 従来案(GitHub Actions上でサーバー側計算): タブを閉じても実行が継続するという利点があったが、依頼者の明確な指示によりクライアントサイド案へ転換した。
- 調整アルゴリズムをTypeScriptへ移植する案: Pyodideを使わずアルゴリズムをTSに書き直す案も検討したが、既存ロジックの逐語移植は再実装リスクを伴うため、Pyodideによる既存Pythonコードの再利用を優先した。

## 2. 対戦履歴インデックスの配布形式とDuckDB-WASMでの参照(FR-002)

**Decision**: `indexer`(GitHub Actionsの定期実行ワークフロー、ユーザー認証情報は一切扱わない)が smash_database リポジトリを定期的に増分取得し、選手ペア単位の対戦タイムスタンプ・大会規模一覧に圧縮した小容量インデックスを **Parquet形式**で生成し、GitHub Releases アセットとして公開する。フロントエンドは調整実行のたびに smash_database 全体を取得せず、この圧縮Parquetファイルのみをダウンロードし、DuckDB-WASMに読み込んでクエリする。近さ指標の計算式(経過時間に対して指数的に減衰)により、一定期間(既定: 数年)より古い対戦履歴は結果へほぼ寄与しないため、インデックスの参照範囲にはこの期間で上限を設ける。

**Rationale**: 現行ノートブックは smash_database 全体をクローンし全大会分のJSONを読み込んでいるが、これは対戦履歴が増え続ける限りいずれメモリ制約に抵触する。対戦履歴全体ではなく「選手ペア→対戦タイムスタンプ一覧」という調整計算に必要な最小限の情報だけを保持すれば、データ量は選手ペアの延べ対戦数に比例する程度に収まり、桁違いに小さくなる。Parquet形式はDuckDB-WASMが効率的に読み込める列指向フォーマットであり、依頼者の「ローカルにデータを全部持ってきて計算する」という意図とも合致する(圧縮済みの小容量インデックスであれば「全部持ってくる」ことがそのまま現実的な選択肢になる)。indexer側では増分更新(前回処理済みの大会以降のみ走査)によって、smash_database自体が大きくても定期実行のたびに全件再走査する必要がなくなる。indexerの実行自体もGitHub Actionsのため無料で、0番の大原則とも整合する。

**Alternatives considered**:
- 実行のたびに smash_database をシャロークローンして都度集計: 履歴データそのものが大会数に比例して増え続けるため、根本的なメモリ制約解消にならず不採用。
- DuckDB-WASMのhttpfs拡張によるリモートParquetへの範囲リクエスト(部分読み込み)でsmash_database相当の大きなデータセットを直接クエリする案: indexerによる事前圧縮(選手ペア単位への集約)を省略できる可能性はあるが、smash_databaseの生データはgitリポジトリ内の入れ子になったJSONファイル群でありDuckDBが直接クエリできる形になっていないため、結局smash_databaseをクエリ可能な形式に変換する前処理コンポーネント(=indexer相当)が必要になる。事前圧縮によりデータ量そのものを削減できるほうが確実にメモリ制約を解消できるため、indexer + 圧縮Parquet配布の現行案を維持する。

### 実測に基づく規模・ダウンロード時間の見積もり(2026-08-21実施)

「計算時間だけでなく、データ取得時間やサイズが現実的か」という懸念に対し、実際の smash_database リポジトリ(GitHub API・raw経由)を調査した。

**調査方法と結果**:
- リポジトリの圧縮サイズ: 約134MB(全大会分の生JSON全体。これは配布物ではなく調査対象データの規模感の参考値)。
- `tournaments.jsonl`(6.6MB)を解析した結果、大会数21,036件・イベント数28,932件(2022年頃から現在までの、日本・北米・欧州等を含む全地域の履歴)。
- イベント40件をランダムサンプリングし(36件で`matches.json`を取得成功)、平均試合数は**1イベントあたり約50試合**。
- これを全28,932イベントに外挿すると、**全期間・全地域で推定約145万試合**。
- 本設計で必要なのは対戦相手ペアの`{winner_id, loser_id, timestamp, numEntrants}`のみ(いずれも整数)であり、1行あたり28バイト(int64×2 + int64 + int32)で表現できる。これは現行ノートブックが読み込む生JSON(1試合あたり実測約390バイト、ゲームごとの詳細情報等を含む)の**約1/14の情報量**に相当する。
- 145万行 × 28バイト ≒ **非圧縮で約40MB**。Parquetの辞書/デルタ圧縮(IDやnumEntrantsの重複が多い列指向データのため圧縮率が高い)を3〜5倍と見積もると、**圧縮後は概ね8〜14MB程度**と推定される。

**この見積もりが意味すること**:
- 「全期間・全地域」を対象にしても、対戦履歴インデックス自体はブラウザで扱うのに何ら問題のないサイズ(数MB〜十数MB)に収まる見込みである。近さ指標の減衰特性による参照期間の上限(例: 直近3〜5年)は、この見積もりに基づけばサイズ上の必須要件ではなく、「古すぎて実質寄与しないデータを含めない」という設計上の潔癖さと、将来的な参加大会数の増加に対する安全マージンとして維持する。
- ダウンロード時間は、一般的な回線(数十Mbps以上)であれば数秒程度と見込まれ、60分の実行時間予算(FR-003)に対して無視できる水準である。
- ブラウザのメモリ・IndexedDBストレージ上限(通常、空きディスクの相当割合まで許容される)に対しても、十数MB程度のデータは実務上まったく問題にならない規模である。

**注記(未検証部分)**: 上記はランダムサンプリング(36イベント)からの外挿であり、地域・大会規模による偏りを完全には排除できていない一次見積もりである。indexerの実装時には、実際に全件を走査した上でこの見積もりを検証し、想定から大きく外れる場合(例: 実際の圧縮後サイズが数十MBを超える)は、参照期間の上限をより積極的に短縮する運用で対応する。

### ランタイム・インデックスのキャッシュ方針

**Decision**: Pyodide・DuckDB-WASMの実行環境(初回ダウンロードで概ね10〜15MB程度)はブラウザの標準HTTPキャッシュにより2回目以降の訪問では再ダウンロードされないようにする。対戦履歴インデックス(Parquet)は、[contracts/match-index-format.md](./contracts/match-index-format.md)のマニフェストが持つ`generatedAt`をキャッシュキーとして用い、同一ブラウザ内で内容が変わっていなければ(indexerが再生成していなければ)再取得しない。

**Rationale**: 同じ運営者が同じ大会に対して複数回実行することは珍しくなく(spec.md FR-016の履歴閲覧機能もこれを前提としている)、毎回十数MBを再ダウンロードするのは不要な待ち時間を生む。indexerの更新頻度(日次〜週次程度を想定)を踏まえれば、キャッシュにより実質的な待ち時間は初回のみになる。

**Alternatives considered**: 常に無条件で最新版を再取得する案もシンプルだが、上記の理由で不要な待ち時間を発生させるため、条件付き取得(マニフェストの生成日時比較)を採用した。

## 3. 状態管理・公開結果キャッシュ(FR-014, FR-012b, FR-016)

**Decision**: Cloudflare Workers(Freeプラン)上に、以下のみを扱う最小限のHTTP APIを実装する。
- 実行の開始・完了/失敗の記録(`AdjustmentRun`。同一対象への複数同時実行を妨げない単純な記録であり、ロックは行わない)
- 調整パラメータ設定(`AdjustmentSettings`)
- クライアントが計算完了後に提出する、公開結果のサニタイズ済みコピー(非公開評価値を含まない)の保管・提供

状態は Cloudflare D1(SQLiteベース)に保持する。**利用者の認証トークン(Google/start.gg)はこのサーバー側のいかなる場所にも保存しない**(4番・5番参照)。

**Rationale**: クライアントサイド化により、以前Workerが担っていた「利用者に代わってGoogle Sheetsを読み書きする」「GitHub Actionsジョブに資格情報を安全に受け渡す」という役割は不要になった。また、当初検討していた「同一対象への多重実行防止ロック」も、その目的(共有計算資源の浪費防止)がクライアントサイド化により該当しなくなったため撤回した(spec.md Clarifications、方針変更2026-08-21)。残るのは、複数の利用者・端末をまたいで共有されるべき状態(実行履歴、認証なしで閲覧できる公開結果)であり、これらに限定した薄いAPIとしてWorkerを残す。Cloudflare WorkersのFreeプランはクレジットカード登録なしで利用開始でき、上限超過時は課金ではなくエラー応答になる(fail-closed)。

**Alternatives considered**: Firestore(Google Cloud)の無料Sparkプランも同様の要件を満たせるが、Google Cloudは0番の方針によりOAuthクライアント登録以外の用途を持たせない方が運用対象を減らせるため、Cloudflare D1に統一する。多重実行防止ロック+ハートビートによる自動失効の設計(前回改訂までの案)は、依頼者との検討の結果、残存リスク(Startgg書き戻し時の後勝ち上書き等)が許容範囲と判断されたため撤回した。

## 4. Google 認証方式(FR-001, FR-017, FR-020)

**Decision**: フロントエンドは Google Identity Services の JS SDK(トークンクライアント、`google.accounts.oauth2.initTokenClient`)を用いて、ブラウザ内で完結する OAuth 2.0 フローによりアクセストークンを取得する。取得したアクセストークンは、ブラウザのメモリ内(実行中のセッションの間のみ)に保持し、そのままGoogle Sheets APIの呼び出しに使う。**サーバー側(Cloudflare Worker)は認可コードの交換もリフレッシュトークンの保管も行わない。**

**Rationale**: 以前の設計では、タブを閉じても継続するバックグラウンド実行のために、ブラウザセッションに依存しない長期的な認可(リフレッシュトークン)をサーバー側で保管する必要があった。計算がクライアントサイド化され、かつ「タブを閉じても継続する」ことが必須要件でなくなった(1番参照)ことで、この長期保管の必要性自体がなくなった。ブラウザ完結のトークンクライアントで得られる短命なアクセストークン(実行中の間は有効)で十分であり、サーバー側に一切のGoogle認証情報を保管しないことで、漏洩リスクの経路そのものを1つ丸ごと排除できる。認証情報の入力はすべて設定ページのOAuth同意画面によるボタン操作で完結し、利用者が環境変数やAPIキーを直接入力する必要はない(FR-017)。各利用者は自分自身のブラウザセッション内のトークンのみを用いるため、他利用者のデータにアクセスできない(FR-020)。OAuthクライアントIDの登録には課金無効なGoogle Cloudプロジェクトを1つ用いる(0番参照)。

**Alternatives considered**: 従来の認可コードフロー+サーバー側リフレッシュトークン保管(前回改訂までの案)は、タブを閉じても継続する実行を前提としていたが、その前提がなくなったため不要になった。サービスアカウントによる共有アクセスは、FR-020(利用者自身の権限範囲でのみアクセス)に反するため引き続き不採用。

## 5. start.gg 連携の認証方式・トークン保管(FR-010, FR-011, FR-017)

**Decision**: 設定ページで、利用者自身が発行した start.gg 個人アクセストークン(Bearer token)を入力する方式を採用する。このトークンは**ブラウザのローカルストレージ(IndexedDB)にのみ保存し、いかなるサーバー(Cloudflare Worker等)にも送信・保存しない**。調整実行時、フロントエンドはこのトークンを使ってブラウザから直接 start.gg の GraphQL API を呼び出す(6番のCORS対応状況による)。

**Rationale**: サーバー側が一切の認証トークンを扱わなくなったことで(4番と同じ設計思想)、start.ggトークンについても「サーバーに預けない」という、以前の設計よりもさらに単純かつ強い漏洩防止策を取れる。利用者から見ても「自分のトークンは自分の端末の外に出ない」という説明がしやすく、信頼を得やすい。トークンの入力は設定ページのフォームを通じて行われるため、FR-017(環境変数の直接編集をさせない)の要件は満たされる。書き戻し実行時にはトークンに紐づくアカウントの大会運営権限を start.gg 側のAPI呼び出し結果から確認し、権限不足時はFR-021に従い書き込みを行わない。

**漏洩防止の具体策**:
- ブラウザのIndexedDBに保存し、送信は start.gg 自身のAPIエンドポイント(および6番のリレーを使う場合はそのリレーのみ)に対してのみ行う。
- Cloudflare Worker・GitHub Actionsいずれのログにもトークンが記録されることはない(そもそも到達しないため)。
- 伝送はHTTPS(TLS)のみを許可する。

**Alternatives considered**: OAuthアプリとしての正式提供は、アプリ登録・審査のリードタイムが不確実であり、それ待ちで機能提供を遅らせるのは本機能の目的(誰でもすぐ使える)に反するため、採用しない。サーバー側(D1)への暗号化保存(前回改訂までの案)は、サーバーに一切の認証情報を置かないという、よりシンプルで強い方針へ転換したため不要になった。

## 6. start.gg APIのCORS対応リスクと薄いリレーのフォールバック(未検証リスク)

**Decision**: start.gg の GraphQL API(`https://api.start.gg/gql/alpha`)が、GitHub Pagesのオリジンからのブラウザ直接呼び出し(CORS)を許可しているかどうかは未検証であり、実装着手前に検証が必要なリスクとして明記する。もし許可されていない場合は、Cloudflare Worker上に**資格情報を保持・ログ保存しない薄いリレー**(`POST /relay/startgg`: リクエストボディとAuthorizationヘッダをそのまま start.gg APIへ転送し、レスポンスをそのまま返すだけの中継。トークンを含むリクエスト内容を一切ログに残さない)を用意し、それ経由で呼び出す。

**Rationale**: Google Sheets API(`sheets.googleapis.com`)はブラウザからのOAuthトークン付き直接呼び出しをCORSで許可することが広く知られている標準的な利用パターンだが、start.ggのAPIについては同様の前提が成立するか未確認である。CORSが許可されていない場合、ブラウザから直接呼び出すことができず、何らかの中継が必要になる。ただしこの場合でも、リレーはリクエストを右から左に転送するだけで、トークンを保存も記録もしないため、5番で定めた「サーバーにトークンを預けない」という原則の精神(=サーバー側に永続する秘密を作らない)は損なわれない。

**Alternatives considered**: リレーを常に経由する設計を最初から採用する案も検討したが、直接CORS呼び出しが可能であれば往復1つ分のレイテンシとWorker呼び出し回数(無料枠消費)を削減できるため、検証の上でCORS対応が確認できればリレーを省略する設計とした。

## 7. 認証なしで結果を公開する方法(FR-012b, FR-016, SC-008)

**Decision**: シード自動調整が完了すると、フロントエンド(ブラウザ)は非公開評価値(hidden_value)を除いた調整結果・判断根拠ログ・Wave制約違反記録・(start.gg入力の場合は)調整前シード記録を整形し、`POST /runs/{runId}/complete` としてCloudflare Workerへ提出する。Workerはこれをそのまま D1 に保存する。結果表示ページ(認証不要)は `GET /public/results/{runId}` を呼び出し、Workerが D1 に保存済みのこのサニタイズ済みコピーをそのまま返す。

**Rationale**: サーバー側がもはや利用者のGoogle認証情報を持たないため(4番)、以前の設計(Workerが監査ログ用スプレッドシートを都度取得して整形する方式)は成立しなくなった。代わりに、計算を行った当のブラウザ自身が「非公開項目を除いた公開用の結果」を作成できる立場にあるため、計算完了時にその成果物をそのままWorkerへ提出させる。これにより、hidden_valueのような非公開項目を構造的に除外できる点(FR-012b)は維持しつつ、サーバー側の認証情報保管を一切不要にできる。

**Alternatives considered**: スプレッドシート自体を「リンクを知っている全員が閲覧可」に設定し、閲覧のたびにフロントエンドが直接読み取る方式は、hidden_value列を誤って公開してしまうリスクがあり不採用(以前からの判断を維持)。

## 8. 大規模大会での事前警告(FR-003a、拒否は行わない)

**Decision**: 実測ベンチマーク(想定される参加者数と処理時間の関係。運営者の一般的な端末性能を基準とする)から導いた「想定処理時間が60分を大幅に超えると見込まれる参加者数のしきい値」をフロントエンドの設定値として持つ。実行開始時にこのしきい値を超える場合でも**実行は拒否せず**、「想定処理時間が長くなる可能性があります。実行中はこのタブを開いたままにしてください」という警告を表示した上で、運営者の意思でそのまま実行を継続できる。

**Rationale**: 依頼者から「拒否ではなく警告のみとし、60分を超えてもよいので実行できるようにしてほしい」との明確な指示があり、この方針を維持する。計算がクライアントサイド化されたことで、警告の文言には「タブを開いたままにしてください」という、以前は不要だった注意喚起が新たに必要になる(1番の希望要件化と表裏一体)。

**運用上のトレードオフ(意図的に許容)**: 大規模大会では、運営者の端末で長時間タブを開いたままにする必要が生じうる。以前案にあった「GitHub Actionsのジョブタイムアウト」「他利用者との同時実行枠の競合」という技術的リスクはクライアントサイド化により解消された一方、新たに「運営者の端末がスリープする」「誤ってタブを閉じてしまう」といったリスクが生じる。これらが起きた場合、システムはそれを能動的に検知するわけではなく(多重実行防止ロック・ハートビート機構は撤回済み。3番参照)、運営者が結果を確認できないことに気づいた時点で改めて実行し直す形で対応する(FR-013・US2 Acceptance Scenario 3)。

**Alternatives considered**: 事前拒否を行う案は、依頼者の明確な意向により不採用。仕様レベルで固定の参加者数上限を定める案も、最適化の余地を狭めてしまうため見送った。

## 9. フロントエンド技術選定

**Decision**: TypeScript + React + Vite による静的SPAとし、`vite build` の出力を GitHub Pages にデプロイする。調整アルゴリズムの実行には Pyodide、対戦履歴インデックスのクエリには DuckDB-WASM を用いる(いずれも実行ボタン押下時に遅延読み込みし、通常のページ閲覧・結果表示ページの閲覧には読み込まない)。

**Rationale**: GitHub Pages は静的ファイルのホスティングのみをサポートするため、ビルド時に完全な静的アセット一式を出力できるフレームワークが必要。Reactはエコシステム・採用実績が豊富で、設定ページのYes/Noウィザードや結果表示ページの表形式UIの実装に十分な部品(フォーム、テーブル)が揃っている。Pyodide・DuckDB-WASMはいずれもブラウザで動くWASMランタイムとして確立された選択肢であり、1番・2番の判断と整合する。GitHub Pagesは静的ホスティングのみで課金対象の可変コンピュートを持たないため、0番の大原則とも自然に整合する。

**Alternatives considered**: Svelte/Vueも静的出力可能で有力な代替だが、機能要件上の優劣はなく、今回はエコシステムの厚さを優先してReactを選定した。調整アルゴリズムをPyodideではなくTypeScriptへ移植する案は、1番で述べた再実装リスクの理由により見送った。

## 10. コスト最小化の全体方針(SC-005) まとめ

**Decision**: アーキテクチャを構成する全コンポーネント(GitHub Pages、GitHub Actions[indexerのみ]、Cloudflare Workers/D1、Google Cloud[OAuthクライアント登録のみ・課金無効])のいずれについても、運用担当者は支払い手段(クレジットカード等)を一切登録しない。無料枠を超えた場合の挙動は「機能の一時的な利用不可(エラー・キュー待ち)」であり、実費請求は構造的に発生しない。加えて、重い計算そのものが運営者の端末で行われるため、サーバー側で課金対象になりうる計算資源が最初から存在しない。

**Rationale**: 依頼者の「料金をできる限り支払いたくない」という要望に対し、「無料枠に収まる見込み」という運用上の期待ではなく、「そもそも支払い手段が登録されていないため課金されようがない」「重い計算はそもそもサーバーで行わない」という二重の設計上の性質でSC-005を保証する。将来的にサーバー側コンポーネント(Cloudflare Workers/D1)の無料枠でも足りなくなった場合は、それを機能改善の意思決定として扱えばよく、意図せず費用が発生することはない。
